# 0003 · CI/CD avec GitHub Actions

- Date : 2026-11-04
- Statut : accepté
- Auteurs : Syrine, Maryem

## Contexte

Jusqu'à la tâche 8, c'est la personne qui relit une PR qui lance les tests et le build Docker
sur son PC. C'est long, et on peut oublier une étape. On veut que GitHub le fasse
automatiquement, et qu'une PR qui casse quelque chose ne puisse pas être fusionnée.

## Décision

**CI (`.github/workflows/ci.yml`), à chaque PR vers `main` et à chaque fusion :**
1. job « Lint et tests » : `ruff check`, `ruff format --check`, `pytest`
   (Python 3.12, PyTorch CPU, versions figées dans `api/requirements-test.txt`) ;
2. job « Build Docker et test de fumée », seulement si le 1ᵉʳ job passe :
   `dvc pull` des deux modèles depuis DagsHub, `docker build`, `docker run`, puis
   `scripts/smoke_test.py` appelle `/health`, `/info`, `/predict` et la page web.
   Il vérifie aussi que les md5 des modèles dans l'image sont ceux de `dvc.lock`.

**CD (`.github/workflows/cd.yml`), à chaque tag `v*` :** même build et même test de fumée,
puis l'image est publiée sur GitHub Container Registry
(`ghcr.io/sirinebbj123/waste-sorting-mlops:<tag>` et `:latest`) et la Release du tag
est créée automatiquement.

**Protection de `main` :** les deux jobs de la CI sont des *status checks* obligatoires,
en plus de la relecture par l'autre membre.

**Secrets :** le token DagsHub est un *secret* GitHub Actions (`DAGSHUB_USER`,
`DAGSHUB_TOKEN`), jamais écrit dans le code. Il sert uniquement au `dvc pull` et n'entre pas
dans l'image (`.dockerignore` exclut `.dvc/config.local`). La publication sur ghcr.io
utilise le `GITHUB_TOKEN` temporaire fourni par GitHub.

## Pourquoi ces choix

- **GitHub Actions** : déjà là où est le code, gratuit pour nos besoins, rien à installer.
- **PyTorch CPU en CI** : les machines GitHub n'ont pas de GPU, et la version CPU
  s'installe beaucoup plus vite.
- **Tests sans les modèles dans le 1ᵉʳ job** : rapides (faux pipeline). Le vrai modèle
  est testé dans le 2ᵉ job, dans l'image Docker, comme en production.
- **ghcr.io plutôt que Docker Hub** : pas de compte en plus, l'image est liée au dépôt.
- **Publication seulement sur un tag** : une image publiée = une version choisie et nommée.

## Conséquences

- Une PR prend quelques minutes de plus avant d'être fusionnable (la CI doit passer).
- Si le token DagsHub expire, le job Docker échoue : il faut créer un nouveau token et
  mettre à jour le secret `DAGSHUB_TOKEN`.
- N'importe qui peut lancer la dernière version : `docker pull ghcr.io/sirinebbj123/waste-sorting-mlops:latest`.
